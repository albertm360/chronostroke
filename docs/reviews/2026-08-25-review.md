## Executive summary

ChronoStroke is a WPF/.NET 10 keystroke repeater that injects scan codes through hand-written
`SendInput` interop and toggles via a `RegisterHotKey` global hotkey. It is, for its size, an
unusually mature codebase: the interop layer is correct in exactly the places that fail silently at
runtime, the repeat loop's key-release guarantee holds on every exit path including cancellation,
and the comments record *measurements and rejected alternatives* rather than restating the code. A
prior review ([2026-08-20](2026-08-20-review.md)) was worked through in full, and it shows.

What is left is a different, smaller set of problems. There is one reproducible latent
`NullReferenceException` in the engine's start/stop handoff. There are two safety gaps around the
hotkey — the app will happily start an input flood it has no registered way to stop, and it will
let you bind a bare printable key as a global hotkey and swallow that key system-wide.
`MainViewModel` has grown into the one genuinely unwieldy file, carrying six near-duplicated
members because the interval and step fields were never abstracted. And the settings layer still
writes to disk more often than the 1.1.0 changelog entry claims.

**No Critical findings.** There is no network, database, subprocess, or registry surface (verified
by grep); the only two external-input paths are the keyboard capture box and `settings.json`, and
the latter is deserialized through a source-generated `JsonSerializerContext` over a sealed record
of primitives with no polymorphism. The one real gap there is validation completeness, not
injection, and it is filed as M3.

Verdict: close to top-tier for its category. Fix H1 through H3 and it is genuinely
shippable-with-confidence; the rest is maintainability work that will pay off if the app grows a
fourth or fifth setting.

## High

### H1. `RepeatEngine.Start` reads `_cts.Token` inside the lambda — a `NullReferenceException` race with `StopAsync`

`ChronoStroke/RepeatEngine.cs:56-57`

```csharp
_cts = new CancellationTokenSource();
_loop = Task.Run(() => RunAsync(down, up, intervalMs, triggerCombo, _cts.Token));
```

`_cts.Token` is not evaluated when `Task.Run` is called — it is a field read deferred to whenever
the thread pool dequeues the work item. `StopAsync` sets `_cts = null` before awaiting. If the pool
has not picked up the item by then, the lambda dereferences null.

The fault lands in the task, so `await loop` rethrows it; `StopAsync`'s catch only handles
`OperationCanceledException`, so the NRE propagates out to the dispatcher and the user gets the
unexpected-error dialog. `RunAsync` is never entered, so its `finally` never runs — but nothing was
pressed either, so no key is left held. It is a crash, not a stuck key.

Reproduced in a standalone console app: **NRE on iteration 0**. In the real app the window is much
narrower — a human cannot click Start then Stop inside the pool's dequeue latency, and
`ToggleAsync`'s 250 ms debounce covers the hotkey path. The realistic trigger is thread-pool
starvation during a cold start.

```csharp
var cts = new CancellationTokenSource();
var token = cts.Token;              // read now, on the UI thread
_cts = cts;
_loop = Task.Run(() => RunAsync(down, up, intervalMs, triggerCombo, token), token);
```

### H2. The app will start an input flood it has no registered way to stop

`ChronoStroke/MainViewModel.cs:414-415`

`CanStart` has no term for "a hotkey is actually registered". With none registered, the only way to
stop the loop is to reach the window with the mouse — while the app is injecting a keystroke of the
user's choosing into whatever has focus, every 50 ms. `Alt+Tab`, `Enter` and `Alt+F4` are all
capturable send combos. The first-launch-collision path is entirely plausible: `Ctrl+F8` is taken,
the error banner appears, the user shrugs and clicks Start.

`GlobalHotKey.Current` already tracks the live registration and `ApplyHotkey`'s `finally` already
re-evaluates the command, so this needs no new plumbing:

```csharp
    && _hotKey?.Current.IsEmpty == false;
```

### H3. A bare printable key can be bound as a global hotkey, swallowing that key system-wide

`ChronoStroke/Interop/GlobalHotKey.cs:36-41`

`TryRegister` rejects exactly one key (`F12`) and imposes no modifier requirement. A registered
hotkey is consumed by the OS rather than delivered to the focused window, so a user who taps
`Space` into the hotkey box makes the space bar dead in every application on the machine for as
long as ChronoStroke is open.

> **This finding's suggested fix was wrong and was not used.** It proposed deriving the answer from
> `MapVirtualKeyW` with `MAPVK_VK_TO_CHAR` — reject anything mapping to a printable character.
> Measured before implementing: `Space` returns `' '` (rejected as whitespace), `Enter` `0x0D` and
> `Tab` `0x09` (rejected as control characters), and the arrows, `Home`, `Delete` and `Insert` all
> return `0`, exactly like `F8`. The call cannot separate the dangerous keys from the safe ones,
> and it varies by keyboard layout. What shipped instead names the safe set outright — `F1`–`F24`,
> `Pause`, `ScrollLock`, and the browser/volume/media block — and fails closed.

### H4. `MainViewModel` is the one file that has outgrown the design

`ChronoStroke/MainViewModel.cs` — 489 lines, 25% of the application's source.

It holds settings load/clamp/save orchestration, two independent numeric validators, the hotkey
register/rollback state machine, engine lifecycle, spinner arithmetic, dispatcher marshalling,
status-string formatting, hotkey debouncing, and collision/warning analysis.

The concrete symptom is six near-identical member *pairs*, one for interval and one for step:
`_lastValid*Ms`, `*Text`, `*Error`/`Has*Error`, `On*TextChanged`, `Validate*`, `*OrLastValid`.
`ValidateInterval` and `ValidateStep` differ only in their bounds and message wording. A third
numeric setting would mean a seventh pair.

Two small extractions, both plain classes in the same folder, remove roughly 150 lines:

1. **`BoundedIntField`** — holds `Text`, `Min`, `Max`, a `LastValid` value and an `Error` string;
   owns the parse-clamp-remember logic once.
2. **`HotkeyBinder`** — absorbs `_hotKey`, `_lastGoodHotkey`, `_applyingHotkey`,
   `_hotkeyRegistrationError` and `ApplyHotkey`. That register-fail-roll-back-re-register sequence
   with a re-entrancy guard is the subtlest state machine in the app and deserves to be a named
   thing that can be tested.

## Medium

### M1. Settings still hit the disk far more often than the changelog claims

`MainViewModel.cs:210-236, 240-260, 404-412` → `SettingsStore.cs:51-62`

The `_lastSaved` comparison suppresses writes for *invalid* intermediate values, but not for valid
ones. Typing `100` into the Step box produces `1`, `10`, `100` — three full save cycles. Holding a
spinner arrow (`Interval="80"`) writes about 12.5 times a second. Each write is
`Directory.CreateDirectory` + `File.WriteAllText` + `File.Move`, synchronously, on the UI thread.

A `DispatcherTimer` at ~500 ms, restarted on each change, with a flush in `DisposeAsync`, is about
ten lines and preserves the crash-safety property.

### M2. The `UnobservedTaskException` handler does the opposite of what its comment says

`App.xaml.cs:26-28`

`SetObserved()` with an empty body is the definition of losing a failure without trace. It also
guards against nothing: since .NET Core an unobserved task exception does not tear down the
process. The case its comment cites is already handled correctly — `ToggleFromHotKey` is
`async void` precisely so its exceptions reach the dispatcher, which means they are never
unobserved. Deleting the handler is the honest choice.

### M3. The settings load path validates two of its four fields

`MainViewModel.cs:183-194`, `AppSettings.cs:12, 22`

`IntervalMs` and `IntervalStepMs` are clamped. `SendVirtualKey` and `HotkeyVirtualKey` — both
`ushort`, both from the same hand-editable file — go through unchecked, while `README.md:95-96`
claims "values are re-validated on load". Blast radius is small, but it is the app's only
unvalidated external-input path.

### M4. The two most failure-prone behaviours in the app have no test seam

`SettingsStore.cs:12`, `RepeatEngine.cs:116-158`

- `SettingsStore.FilePath` is `static`, initialised from the real `%AppData%`, so the atomic-write
  and corrupt-file-fallback paths cannot be exercised. An `internal static Load(string path)` /
  `Save(AppSettings, string path)` pair makes the store testable against a temp directory.
- `RepeatEngine` calls `KeystrokeSender.Send` statically, so the app's single most important safety
  property — the key-up in the `finally` firing on every exit path — can only be verified by
  injecting real keystrokes. An `internal Func<INPUT[], SendOutcome> _send = KeystrokeSender.Send;`
  field unlocks tests for key-up-after-cancel-mid-hold, the hold clamp at the 50 ms floor, and
  failure de-duplication.

### M5. Two sources of truth for "is it running"

`RepeatEngine.cs:28, 145-151`; `MainViewModel.cs:119`

They diverge when the loop ends without the view model asking. `RunAsync`'s catch-all reports the
failure and lets the task complete, but `_cts` stays non-null and the view model never hears: the
status line says the loop stopped while the dot stays green and the fields stay locked. Raise a
`Stopped` event from `RunAsync`'s `finally`, or have the view model read through to the engine.

### M6. `OnClosing` sets its re-entrancy guard after the await, not before

`MainWindow.xaml.cs:68-107`

`_shutdownComplete = true` sits after `await _viewModel.DisposeAsync()`. A second close during that
await re-enters with the flag still false and runs the whole sequence again, raising the public
`Closing` event a second time — which the method's own comment says must not happen. Split it: a
`_closing` flag on entry, `_shutdownComplete` for the second pass.

### M7. The validation banner is copy-pasted four times in XAML

`MainWindow.xaml:86-98, 102-114, 175-187, 188-200`

Four 13-line blocks differing only in brush, glyph and bound text — 52 lines where about 20 would
do. A `ControlTemplate` on a `ContentControl` finishes what `BannerStyle` started.

## Low / polish

- **L1.** `<Version>` is two releases stale (`ChronoStroke.csproj:29`). Drop it, or add a CI step
  asserting it matches the newest `CHANGELOG` heading.
- **L2.** `Marshal.GetLastWin32Error()` → `Marshal.GetLastPInvokeError()` (`KeystrokeSender.cs:80`,
  `GlobalHotKey.cs:49`) — the correct spelling for source-generated interop.
- **L3.** `App` is the only public type in an assembly whose types are otherwise internal. Add
  `x:ClassModifier="internal"` to `App.xaml`.
- **L4.** A captured combination can never be cleared from the UI — every `IsEmpty` branch is
  reachable only from a hand-edited `settings.json`. Add a clear affordance or document it.
- **L5.** Engine-to-view-model events carry no run generation, so a status posted just before Stop
  can land after `"Stopped."` and leave a stale message.
- **L6.** `-warnaserror` lives only in CI. Add `<TreatWarningsAsErrors>` to the csproj so the gate
  is felt where the code is written.
- **L7.** `TargetFramework`, `RuntimeIdentifier`, `Nullable` and `ImplicitUsings` are declared
  identically in both projects. A four-line `Directory.Build.props` holds them once.
- **L8.** `Unregister` discards the `UnregisterHotKey` result but sets `_registered = false`
  unconditionally.
- **L9.** No single-instance guard. A second copy loses the `RegisterHotKey` race and reports the
  hotkey as taken by "another application" — true, confusing, and both instances can then inject.
- **L10.** `REVIEW.md` sat at the repository root with every finding resolved. *(Done — this
  directory.)*
- **L11.** Measured, for the record: `InvariantGlobalization` is not a size lever here.
  **61,538,769 bytes baseline vs 61,538,876 with it** — a 107-byte *increase*.

## What's already done well

- **The interop is correct in all the places that fail silently.** `InputUnion` declares
  `MOUSEINPUT` and `HARDWAREINPUT` purely so the union sizes to 40 bytes rather than 32 — the most
  common way a first `SendInput` attempt fails, with no compile-time symptom. `dwExtraInfo` is
  `nuint`. `InputSize` is computed. The `MAPVK_VK_TO_VSC_EX` / `0xE0` / always-extended-list logic
  is right, and the table was *derived by probing* rather than guessed.
- **The `0xE1`/Pause decision.** `KeystrokeSender.cs:111-114` declines to send a plausible-looking
  lie and falls back to virtual-key mode. That is the harder and correct call.
- **The key-release guarantee.** The unconditional `finally`, plus `StopAsync` awaiting the loop
  *past* it, plus the teardown ordering in `DisposeAsync` and `OnClosing`. Engineered, not hoped for.
- **Comments that record decisions, measurements and rejected alternatives** — the
  `PublishReadyToRun` note with its medians and a "re-measure before reconsidering" instruction;
  the `SetResourceReference` explanation; the local-value-beats-template-trigger note. The most
  valuable thing in the repository.
- **Correct async discipline.** `ConfigureAwait` used deliberately in both directions and
  annotated, `PeriodicTimer` over a naive delay loop, cancellation propagated to every await, and
  the one `async void` justified in writing.
- **Atomic settings writes** with exception filters widened deliberately and the reasoning attached.
- **Security hygiene appropriate to the surface:** source-generated JSON with no reflection
  fallback, source-generated interop, `DefaultDllImportSearchPaths(System32)`, per-user `%AppData%`,
  and no network, subprocess or registry surface at all.
- **CI and release discipline** beyond what most commercial repos manage: actions pinned to commit
  SHAs with the reason recorded, `-warnaserror` in the gate, a tag-shape guard, a published
  SHA-256, and a release that *fails* if `CHANGELOG.md` has no matching section.
- **Accessibility was actually done,** not gestured at: `LabeledBy` on all three inputs, `Name` on
  the spinner buttons, and `LiveSetting="Polite"` on the status line with an explanation of why.
- **Dependency discipline.** One production package, zero vulnerable, zero outdated, zero warnings.
- **The README is more honest than most commercial software ships with** — UIPI, anti-cheat, the
  15.6 ms timer resolution, and the "killing the process can leave a key held" caveat all stated
  plainly rather than buried.
